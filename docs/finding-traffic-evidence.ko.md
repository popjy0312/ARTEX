# 취약점 트래픽 증거

취약점 상세의 “연관 트래픽”은 여러 페이지에서 여러 항목을 선택하고, 용도와 설명을 지정하고, 순서를 정하고, 연결을 해제할 수 있습니다. 트래픽 페이지에서도 여러 레코드를 선택해 기존 취약점 하나에 한 번에 연결할 수 있습니다. 작업에서 상속된 취약점 증거는 읽기 전용이며, 수정하려면 원본 작업으로 들어가야 합니다.

시스템 설정의 “Agent 자동 트래픽 연결”은 기본적으로 꺼져 있으며, 읽기 및 수정 API는 `agent_traffic_binding`을 사용하는 `/api/settings`입니다. 켜면 조회 요청/응답, 도구 호출, 프롬프트로 인한 Token 소비가 늘어나고 다음 Agent 실행부터 새 설정을 사용합니다. 끄면 자동 연결 파라미터와 보충 연결 도구를 숨기고 자동 연결 안내를 주입하지 않으며, 이미 실행 중인 세션의 새로운 자동 연결 제출을 거부합니다. 수동 연결, 트래픽 캡처, 저장된 증거 읽기와 내보내기는 영향을 받지 않습니다.

켜진 경우 기본 흐름은 “발견하여 저장 → 보고서 Agent 자동 실행 → 트래픽 확인 및 연결 → 최신 증거 버전으로 보고서 작성”입니다. 보고자는 `evidence`에 검증 명령, 핵심 출력, 이미 존재하는 실제 트래픽 ID와 용도를 보존합니다. 보고서 Agent는 취약점 상세 및 실행 기록을 결합하고 `traffic_search` / `traffic_get`으로 확인한 뒤 `bind_finding_traffic`을 호출하고 최신 `version`을 읽어 보고서를 저장합니다. 스위치가 꺼져 있으면 보고서 Agent는 원시 트래픽 검색/읽기 도구를 추가로 받지 않고 자동 연결도 하지 않습니다. 그래도 수동으로 연결된 스냅샷은 읽고 보고서를 생성할 수 있습니다.

기존 호출자와의 호환성을 위해 `report_finding`의 `traffic_refs` / `evidence_hint_id`를 통한 명시적 즉시 연결은 계속 지원합니다. 연결은 선택 사항입니다. TCP 같은 비 HTTP 취약점, 수집되지 않은 트래픽, 정확한 레코드를 찾을 수 없는 경우에는 참조를 생략해도 정상적으로 보고하고 작성할 수 있습니다. 명령 출력, 로그 등 검증 가능한 다른 증거를 보존하고 연결하지 않은 이유를 설명하는 것이 좋습니다. 필수 필드를 새로 추가하지 않습니다. 제출된 ID는 모두 유효해야 하고 본문은 완전해야 합니다. 하나라도 실패하면 이번 연결 작업 전체를 롤백하며, 보고와 함께 명시적으로 연결하다 실패하면 보고 제출 전체를 롤백합니다. 같은 스냅샷을 다시 추가해도 연결이 늘어나지 않고 설명을 덮어쓰지 않습니다.

## Agent ID와 보고서 버전

`report_finding`에 선택적 파라미터가 추가되며, 배열 순서가 초기 증거 순서입니다.

```json
{
  "traffic_refs": [
    {"traffic_id": "실제 트래픽 ID", "role": "baseline", "note": "정상 계정 요청"},
    {"traffic_id": "다른 실제 트래픽 ID", "role": "proof", "note": "재현 요청"}
  ]
}
```

용도는 `baseline`(정상 대조), `proof`(취약점 증명), `verification`(추가 검증), `supporting`(보조 증거, 기본값)입니다. 먼저 `traffic_search` / `traffic_get`으로 실제 레코드를 확인합니다. 도메인과 시간은 후보를 필터링하는 데만 사용하며 작업 귀속을 추정하지 않습니다.

프롬프트 참고 자료는 [CyberStrikeAI의 취약점 보고 도구 안내](https://github.com/RuoJi6/CyberStrikeAI/blob/54d56774b8bd285817d16d48b70a4a5e6e0963f7/internal/app/vulnerability_tools.go)입니다. 이 프로젝트의 선택적 연결 규칙과 함께 사용하며, 패키지가 없다는 이유만으로 필수 검증을 도입하지 않습니다. ID를 추측하거나 패키지를 채우기 위해 반복 탐색하지도 않습니다.

반환 첫 줄은 여전히 `finding recorded: <탐색 노드 ID>`이며, 이어지는 JSON은 독립 취약점 레코드 `finding_id`, 탐색 노드 `finding_node_id`, 연결 요약을 제공합니다.

- `get_finding_traffic(finding_id)`는 **독립 취약점 레코드 ID**를 사용하며 정렬된 목록과 `version`을 반환합니다. `binding_id`, `side=request|response`, `offset`, `length`를 전달하면 분할 읽기가 가능하고 각 구간은 최대 8192바이트입니다.
- `update_finding_report`의 `finding_id`는 계속 탐색 노드 ID를 사용합니다. 새 `evidence_version`에는 실제로 읽은 버전을 넣어야 합니다. 생성 중 증거가 바뀌면 이전 버전의 쓰기를 거부하므로 다시 읽고 생성해야 합니다.
- 버전을 전달하지 않은 기존 보고 호출은 기존 트래픽 증거를 덮었다고 선언하지 않습니다. 연결, 설명, 용도 또는 순서가 변경되면 기존 보고서에 업데이트 대기 상태를 표시합니다.

자동 연결을 켜면 `add_hint` / `add_task_hint`는 단일 프롬프트 또는 일괄 `hints`의 각 요소에 `traffic_refs`를 저장할 수 있습니다. Planner가 대신 보고할 때 `evidence_hint_id`를 전달하면 이 작업에 해당하는 프롬프트의 참조를 명시적으로 선택할 수 있지만 상속된 프롬프트는 참조할 수 없습니다. 시스템은 도메인, 시간 또는 브라우징 기록으로 연결을 추정하지 않습니다. 제출이 실패하면 일부 취약점을 만들거나 보고서를 미리 실행하지 않습니다.

기존 취약점에 연결이 빠졌다면 다시 등록하지 않고 `bind_finding_traffic(finding_id, traffic_refs)`로 보충합니다. `list_findings` / `list_task_findings` / `node_detail` / `get_task_node_detail`은 명시적인 `finding_id`와 `finding_node_id`를 반환하며, 기존 `id`는 탐색 노드 의미를 유지합니다.

시작 시 기존 도구 스키마에 선택적 속성만 추가하고, 기존 기본 트래픽 도구 연결을 보고서 Agent까지 확장합니다. 보충 연결 도구는 기본적으로 보고서 Agent에 맡깁니다. 사용자 지정 연결 목록, 프롬프트, 설명 및 활성화 상태는 보존합니다. 최종 도구 조립 후 안내를 한 번에 추가합니다. 보고 역할은 기존 증거를 전달하고 보고서 Agent가 확인·연결·보고서 작성을 담당합니다. 플랫폼 대화에 작업 맥락이 없으면 직접 보고하지 말고 구조화된 프롬프트로 작업 Agent에 전달해야 합니다. 작업 완료를 판단하기 전에 기존 증거를 먼저 전달해야 하며, 패키지가 없다고 강제로 기다리지는 않습니다. 실패한 `report_finding`은 보고서 Agent를 실행하지 않습니다.

## API

기본 경로는 독립 취약점 ID를 사용하는 `/api/exploration/findings/{finding_id}/traffic`입니다. 기존 인증을 따르며 `context_task`가 작업 가시성과 상속된 읽기 전용 여부를 검증합니다.

| 메서드 / 상대 경로 | 요청 / 반환 |
| --- | --- |
| `GET` | 정렬된 요약, 증거 버전, 보고서가 채택한 버전 |
| `POST` | `{"traffic_refs":[...]}` 일괄 추가 |
| `PATCH /{binding_id}` | `{"version":1,"role":"proof","note":"설명"}` |
| `DELETE /{binding_id}` | `{"version":1}` |
| `PUT /order` | `{"version":1,"binding_ids":["2","1"]}`, 반드시 전체 목록이어야 함 |
| `GET /{binding_id}` | 스냅샷 메타데이터와 제한된 본문 미리보기 |
| `GET /{binding_id}/body` | `side`, `offset`, `length`; `download=1`은 원본 바이트 전체를 다운로드 |

버전/순서 집합 충돌과 보관 중 쓰기는 `409`, 상속 데이터에 대한 쓰기는 `403`, 존재하지 않거나 취약점에 속하지 않는 연결은 `404`를 반환합니다. 트래픽/첨부 파일 읽기 및 검증 실패는 명확한 오류를 반환합니다.

## 저장소와 마이그레이션

시작 시 멱등적인 PostgreSQL 마이그레이션을 실행해 `traffic_evidence_snapshots`, `finding_traffic_bindings`, `findings.evidence_version` / `report_evidence_version`(기본값 0)을 추가합니다. 과거 텍스트를 바탕으로 연결을 추정하지 않습니다.

스냅샷에는 원래 트래픽 ID, 수집 시각, URL, 메서드, 상태, 요청/응답 헤더, 본문 길이와 SHA-256을 저장합니다. 본문은 해시를 기준으로 `<data>/evidence/blobs/<앞 두 자리>/<hash>.bin`에 저장하며 정리 대상인 `data/traffic`과 분리됩니다. 여러 취약점이 스냅샷/본문을 공유할 수 있습니다. 스냅샷에는 내용 갱신 API가 없고 검증이 일치하지 않으면 읽기와 내보내기가 실패합니다.

기존 트래픽 쓰기 잠금 아래에서 대용량 본문 blob과 이전 디렉터리 레코드를 포함한 전체 본문을 읽습니다. 파일을 먼저 영속화하고 검증한 다음 단일 PostgreSQL 트랜잭션으로 탐색 노드, 의도 관계, 취약점, 스냅샷과 연결을 기록하고, 커밋 후에만 Planner에 알립니다. 실패하면 참조되지 않는 파일이 남을 수 있지만 일부 업무 레코드는 만들지 않습니다.

PostgreSQL advisory lock `7337741004`가 증거 파일과 SQL 참조를 조정하며, 작업 행 잠금은 보관 대기 후 증거가 수정되는 것을 막습니다. 복구는 본문 설치부터 메타데이터 커밋까지 증거 잠금을 유지합니다. 취약점 삭제 시 연결은 연쇄 삭제됩니다.

정리기는 매시간 실행되며, 진행 중 작업에 속하지 않고 참조도 없는 콘텐츠만 최소 24시간 지연 후 회수합니다. 일반 트래픽 정리는 증거 디렉터리를 건드리지 않습니다. 핫 데이터를 백업할 때 PostgreSQL과 `data/evidence`를 함께 백업합니다.

## 내보내기와 보관

Markdown에는 정렬된 증거 목록과 버전이 들어가고 JSON에는 메타데이터가 들어가며 CSV에는 개수와 연결 ID가 추가됩니다. `md-zip`은 취약점 Markdown을 보존하고 다음을 제공합니다.

```text
evidence/<finding_id>/<binding_id>/
  manifest.json
  request.http
  response.http
  request.bin
  response.bin
```

Markdown은 상대 링크로 메시지를 참조합니다. 다운로드를 보내기 전에 첨부 파일 복사, 해시 검증, 압축, 디스크 동기화 및 모든 ZIP 항목의 CRC 읽기 검증을 완료해야 합니다. 누락/손상은 전체 다운로드를 실패시킵니다. 완전한 첨부 파일은 원본 바이너리 바이트를 보존합니다.

보관 v3은 원래 트래픽이나 도메인에 의존하지 않고 취약점 연결 관계로 스냅샷과 본문을 수집합니다. 패키지 검증이 완료된 뒤에만 핫 데이터를 정리하고 공유 증거는 계속 보존합니다. 복구는 먼저 설치된 본문을 검증한 뒤 메타데이터와 연결을 트랜잭션으로 복원하며 실패 재시도를 지원합니다. v1/v2도 계속 복구할 수 있고, 새 필드가 없으면 명시적으로 0을 채웁니다.

## 검증과 범위

각 테스트 패키지에 독립적으로 새로 만든 PostgreSQL 테스트 DB를 지정하고 `ARTEX_PG_DSN`으로 설정해, 남은 작업/모델 fixture가 백그라운드 실행을 일으키지 않게 합니다. 관련 패키지를 전체 테스트하고 설정 누락으로 건너뛴 항목이 없는지 확인합니다.

```sh
# 각 패키지를 실행하기 전에 ARTEX_PG_DSN을 해당 독립 테스트 데이터베이스로 설정합니다. 명시적 설정이 실패하면 오류를 발생시켜야 합니다.
go test ./<package> -count=1
go test -race -p 1 ./evidence ./db ./agent ./server -run 'TestEvidence|TestFindingTraffic|TestFindingEvidence|TestReportFindingAtomicContract|TestTaskArchive'
```

프론트엔드 검증에는 `npx tsc --noEmit`, 영향받은 파일의 Biome 검사, Webpack 빌드, `NEXT_EXPORT=1` 정적 내보내기가 포함됩니다. 실행 중인 개발 서비스를 덮어쓰지 않도록 독립 캐시 디렉터리를 사용합니다.

로컬 종단 간 검수는 독립 포트, 제어된 HTTP / 도메인 HTTPS 대상, 임시 데이터 디렉터리를 사용합니다. 두 연결 진입점, 여러 페이지 선택, 순서/설명, 오류 표시, 상속 읽기 전용, 다운로드, 원래 트래픽 삭제 후 내보내기·보관·핫 본문 회수·복구 및 해시 검증을 다룹니다.

첫 버전은 전역 증거 조정 잠금을 사용합니다. 대량 연결/내보내기 또는 느린 첨부 파일 다운로드 중에는 다른 증거 작업이 기다릴 수 있습니다. 녹화 기록이나 완전한 본문이 없으면 증거를 만들어낼 수 없습니다. 이 기능은 캡처 스위치를 변경하지 않으며 HTTPS로 IP에 직접 접근할 때의 인증서 문제도 처리하지 않습니다.
